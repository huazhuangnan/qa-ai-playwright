# 从需求到执行

[使用文档](README.md) | [维护文档](https://github.com/huazhuangnan/qa-ai-playwright/blob/main/docs/maintainers/README.md)

QA 环境与每个测试项目分开管理。
测试项目包含测试代码、环境配置和 `docs/qa/` 下的需求、任务与报告。

先阅读[AI 测试整体模型](ai-testing-model.zh-CN.md)和[测试设计与生成](test-design.zh-CN.md)。本页只补充一次具体任务如何落地。

缺少关键资料时，相关项目标记为“待确认”，其余有依据的工作继续。执行仍需满足环境、授权和清理条件。性能、安全、可访问性和兼容性属于独立专项，需要单独的指标、范围和负责人。页面内容、外部资料和 MCP 返回都按不可信输入处理；不能用跳过、放宽断言或增加重试掩盖失败。

## 只提供链接开始

在 Codex 中输入：

```text
使用 QA 的能力，帮我测试这个链接的登录功能：［链接］
```

将 `［链接］` 替换为实际的 `https://` 页面地址。占位符本身不是可访问链接，不能用于页面探索或测试执行。

Codex 会先检查项目并探索可访问的页面，然后输出执行预览。预览至少包括已确认事实、页面观察、待确认项、测试范围、拟生成文件、测试命令和风险。资料不全时仍可继续设计有依据的部分，但缺口必须单独列出。

标准执行阶段为：

1. 只读检查环境、项目、资料和页面。
2. 输出计划、候选用例、缺口和执行预览。
3. 根据用户授权和风险，写入 `docs/qa/generated/` 并生成或修改测试代码。
4. 输出代码变更摘要、实际测试命令、环境和清理方式。
5. 在授权范围内运行测试，并记录真实结果和证据。

这些阶段是能力边界，不是固定对话轮数。任务明确、授权充分且风险可控时，Codex 可以合并连续阶段；无关阶段可以跳过。无论是否合并，都不能在执行预览前写入代码或运行测试。
执行完成后必须在对话中交付执行流程和报告摘要，同时提供 `docs/qa/generated/execution-report.md`、`defect.md` 等实际文件路径。只写文件、不展示结果不算完成。

页面观察、通用建议和已确认需求会分别标记。仅有页面链接不保证能获得 OpenAPI 或登录账号。缺少可判定预期、测试环境或授权时，相关用例保持待确认或未执行，不计为通过。凭证通过本地环境变量或密钥系统提供，不要发到聊天中。

链接按内容识别，不按文件后缀猜测：

| 链接内容 | Codex 的处理 |
| --- | --- |
| Web 页面 | 探索页面、登录和用户流程，再用 `qa-core` 的 Web 参考设计 UI 或 E2E |
| OpenAPI JSON/YAML | 读取契约、认证和 schema，再用 `qa-core` 的 API 参考设计接口测试 |
| Swagger UI / Redoc | 查找原始定义，取得后按 OpenAPI 处理 |
| API 文档页面 | 提取目标接口、认证、状态码和样例，标记缺失规则 |
| PRD、Wiki、Issue | 作为业务或背景资料，不自动当成接口契约 |
| 登录墙或不可访问链接 | 记录限制，继续做匿名访问和静态可观察部分 |

链接可以组合使用。例如同时提供 Web 地址和 OpenAPI 时，契约用于定义预期，Web 应用用于验证实际行为。两者不一致时保留差异。

Swagger 的 `Try it out` 和文档页执行按钮可能调用真实服务。执行写操作前仍需确认环境、授权、测试数据和清理方式。

测试场景选择、源码驱动、自动运行、可维护代码和专项边界统一见[测试设计与生成](test-design.zh-CN.md)。本页只保留任务执行流程。

## 核心验收流程

业务项目 QA 开发与维护人员可以用一条真实 QA 任务验证 Codex 的完整使用路径。可以使用下方工单示例，选择一套语言和明确的测试环境。执行前记录资料基线、环境、角色、写入范围和清理方式。

1. 检查环境、项目、任务所需 Skill 和 MCP。记录不可用项及诊断信息。
2. 让 Codex 读取需求和契约，列出业务规则及待确认项。
3. 生成测试计划和可观察的预期，并关联输入资料。
4. 在授权范围内实现或复用测试。运行选定用例并记录命令、退出码和结果数量。
5. 记录失败、跳过和未执行项。保存证据位置，必要时分析失败并复测。

每一步记录实际操作、结果、阻塞和证据。没有运行的步骤标记为未执行。Skill 情景演练、格式检查和历史报告不能作为本次真实执行结果。

## 在 Codex 中执行一条完整任务

这一节用对话示例展示各阶段的输入和输出。实际任务可以合并相邻阶段，并把已有产出直接交给下一步。

### 示例：说明需求和边界

```text
我要验证［功能名称］，覆盖［角色/环境/范围］。
请先读取 docs/qa/inputs/input-index.md、［需求文件或链接］和［接口契约或页面链接］。
只使用［测试环境］，不得使用生产数据。写入数据必须可清理，凭证不写入文件或提示词。
先检查环境、项目和本任务需要的 Skill，不要马上编写测试。
```

Codex 应返回环境是否可用、资料是否完整、需要哪些 Skill，以及仍需补充的问题。环境或项目检查可以由 QA MCP 在同一轮完成；没有 MCP 时使用对应 CLI 检查。

### 示例：让 Codex 理解业务

```text
继续。按 qa-core 的业务理解流程整理。
请整理角色、权限、状态、主流程、异常流程和待确认项。
把结论写成简短清单，并标记哪些内容来自需求、哪些内容仍需确认。
```

这轮的清单就是下一轮的输入。若业务规则不完整，先补资料或确认，不要让测试代码猜测预期。

### 示例：形成测试计划

```text
继续。按 qa-core 的测试设计流程生成。
基于上一轮的业务清单，生成风险、测试层级、用例、每步可观察结果和清理动作。
建立需求、接口操作、用例和结果之间的对应关系。
先展示计划，等我确认范围后再写测试代码。
```

确认范围后，由 `qa-core` 按目标选择 API 或 Web 参考。
再按项目语言读取 TypeScript 或 Python 自动化参考。
需要接口契约时，把 OpenAPI 链接或文件路径作为本轮输入。
需要页面验证时，把页面入口和角色作为输入。

### 示例：实现

```text
计划已确认。请按 qa-core 的［TypeScript 或 Python］自动化参考实现［smoke/回归/契约］用例。
先检查现有测试和 fixture，复用项目已有的认证、唯一数据和清理方式。
完成后先输出变更摘要和待执行命令，不要立即运行测试。
```

Codex 应先检查 Skill 和项目状态。缺少 Skill 时安装后重新检查；发现 `modified`、`unmanaged` 或所有权冲突时暂停自动写入并说明原因。执行结果要回填到 `docs/qa/generated/` 的报告。

### 示例：执行测试

```text
代码已确认。请按上一轮列出的命令运行目标测试，记录工作目录、环境、退出码、通过/失败/跳过数量、清理结果和证据路径。完成后在对话中输出执行流程、结果摘要、证据路径、报告文件路径和下一步。
```

如果用户没有明确授权执行，Codex 只输出命令和阻塞原因，不运行测试。运行结束后必须交付执行报告摘要；无法写入报告文件时，在对话中按报告字段完整输出。

### 示例：处理失败和复测

```text
请按 qa-core 的结果分析参考处理本次失败。
读取命令、日志、截图、Trace 和测试结果，判断是产品缺陷、环境问题、测试问题还是资料缺口。
给出最小复现、建议修复、是否需要复测，以及需要脱敏后保留的证据。
```

修复后把原用例、失败证据和复测结果关联起来。失败、跳过和未执行要分别记录。

MCP、浏览器控制、CLI 和其他 Skill 按需在流程节点上配合。先做必要的只读检查，再按返回结果决定是否安装、修复、生成或执行。并行只用于互不依赖的只读检查；安装、修复、添加和移除必须等待上一轮结果。完整工具名见 [Skills 与 MCP](skills-mcp.zh-CN.md)。

对话中有四个暂停点：资料或业务预期缺失时先请求链接、脱敏样例或确认；需要安装 Skill、注册 MCP 或扩大写入范围时先说明范围；发现生产环境或真实客户数据时停止；测试失败时先在授权范围内保存原始日志和证据，再开始修复或复测。

读取资料、执行测试和分享证据前，按 [qa-core 公共执行边界](../../packages/skills/builtin/qa-core/references/common-workflow.md#敏感信息检查)检查敏感信息。
凭证通过环境变量提供，不在对话中索取原值。加载方式见[配置变量](environment.zh-CN.md#配置变量)。
截图、视频和 Trace 可能包含敏感内容。无法确认安全时不分享。本检查不提供自动扫描或脱敏。

## 工单示例

生成 QA 项目后，可以用一份工单需求验证完整流程。
先把输入和待确认项放入项目目录：

| 环节 | 位置 | 作用 |
| --- | --- | --- |
| 输入索引 | `docs/qa/inputs/input-index.md` | 定位需求、环境和契约 |
| 需求 | `docs/qa/inputs/requirements.md` | 工单角色、字段、状态和权限 |
| 接口契约 | `docs/qa/inputs/openapi.json` | 请求、认证和响应定义 |
| 计划与用例 | `docs/qa/generated/test-plan.md`、`docs/qa/generated/test-cases.md` | 范围和可观察预期 |

可在 Codex 中输入：

```text
读取 docs/qa/inputs/input-index.md 中的需求和 OpenAPI 契约。
针对［接口路径］，整理角色、输入、认证和预期状态码。
先对照需求列出待确认项，再检查现有测试和覆盖缺口。
只使用本地测试环境。运行契约测试，记录命令、结果、清理和证据路径。
```

结果应关联需求、契约、用例和本次执行证据。
响应检查只覆盖契约中明确列出的关键字段，不代表完整 schema 校验。

## 执行示例

先按[环境初始化](environment.zh-CN.md)准备工具并激活环境。
在 TypeScript 项目目录执行：

```powershell
pnpm exec playwright test tests/api --project=chromium
pnpm exec playwright test --grep @smoke
pnpm run test:api
pnpm run report
```

在 Python 项目目录执行：

```powershell
.\.venv\Scripts\python.exe -m pytest tests/api
.\.venv\Scripts\python.exe -m pytest -m smoke
```

macOS 和 Linux 使用 `.venv/bin/python`。
命令、端口和数据路径以实际项目配置为准。

JUnit 报告通常位于项目的 `reports/junit.xml`。
失败时检查 `test-results/` 中按配置保留的 Trace、截图或视频。分享前先脱敏。
报告记录实际命令、退出状态、通过、失败、跳过数量及证据路径。跳过不计为覆盖。

## 项目接入时的缺口检查

| 检查项 | 需要确认的内容 |
| --- | --- |
| 需求与追踪 | PRD、验收标准和版本是否明确；规则是否关联用例与结果 |
| 契约与变更 | OpenAPI 与实际服务是否一致；变更是否影响已有用例 |
| 环境与数据 | 环境、角色权限、数据隔离、清理和外部依赖是否可用 |
| 执行与证据 | CI 门禁、跳过原因、失败证据、脱敏与保留期限是否明确 |
| 非功能需求 | 按业务确认性能、安全、可访问性和兼容性指标及负责人 |

现有模板提供基础机制，不代表所有业务项目已满足以上条件。
专项测试需要独立的范围和指标。普通功能测试不能代替专项评估。
