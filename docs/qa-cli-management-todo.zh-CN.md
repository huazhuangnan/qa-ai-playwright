## 优先级

### 核心闭环

- 准备并检查执行 QA 所需的环境、项目、Skill 和 MCP。
- 让 Codex 基于需求和测试环境完成测试设计、执行、失败分析与证据记录。
- 优先修复阻碍上述流程的问题。检查结果应说明失败原因和可执行的下一步。
- 在 GitHub Actions 验证初始化、重复执行、项目生成、所需 MCP、测试执行和用户文件保护。分别报告配置覆盖和实际运行结果。
- 用[核心验收流程](qa-workflow.zh-CN.md#核心验收流程)记录真实任务的结果。场景清单和格式检查不能代替实际执行。

### 可选能力

- Agent Browser、CC Switch、其他 MCP 和双语言示例按实际 QA 需求使用。
- 升级建议、快照和回滚保持现有兼容行为。是否扩展先看真实使用需求。

### 暂缓扩展

- 跨环境全面枚举、所有组件的统一生命周期及全部 MCP 的统一管理。
- 共享软件自动卸载和通用自动回滚。

下方清单保留已有能力和已发现的缺口，供评估使用。只有影响核心闭环或存在明确使用需求的项目才进入实施计划。已有的所有权检查和用户文件保护继续保留。

## 当前实现基线

- 环境和项目已有 `init`、`check`、`uninstall`。
- 可选 MCP 已有 `list`、`check`、`add`、`repair`、`remove`。
- `update check` 和 `skills check-updates` 只读比较来源基线与上游候选版本，不代表已安装版本。
- `project plan` 可只读比较项目文件与当前模板。项目、环境 uv 和内置 Skill 的“升级”命令只提供检测结果和人工操作建议；快照回滚用于恢复人工变更。外部 Skill 使用上游工具。
- `env uninstall` 清理可确认属于当前环境的 MCP 注册，保留环境目录及其数据。成功卸载后状态标记为未初始化。
- `project uninstall` 保留 `.venv`、`node_modules` 和修改文件，并在存在受管保留项时保留项目标记。
- 外部软件卸载不再交互询问。`--include-external` 暂时拒绝执行，因为现有锁记录无法可靠证明外部软件未被其他环境使用。
- 当前命令使用 `skills`。下文未实现的命令名称仅表示管理目标。

## 目标

让 Codex 能可靠使用完成 QA 所需的环境、项目、Skill 和 MCP。CLI 提供必要的初始化、检查和修复入口。版本升级由维护者按检测结果人工执行。

每个动作都要说明作用域、来源、目标版本、当前状态、变更内容和失败处理。
CLI、内置 QA MCP 和文档对已有行为保持一致。优先统一核心流程的错误和结果。

## 统一状态模型

每个受管理对象至少需要以下状态：

- `missing`：未安装或未生成。
- `installed`：已安装，版本和哈希符合记录。
- `outdated`：存在可用的新版本或提交。
- `modified`：用户修改了受管理文件。
- `broken`：文件、入口、配置或依赖不完整。
- `blocked`：缺少环境、权限、网络或用户输入。
- `unknown`：无法安全确认来源或所有权。

这些状态可同时存在。例如组件可以已安装、已修改且有更新。实现时分别报告安装、完整性、更新与可用性维度。
检查结果必须区分“组件管理成功”和“业务测试通过”。

## 统一锁记录和所有权

- 安装记录按对象记录名称、类型、scope、来源、实际版本或提交、所有权和安装位置。可获取时记录许可证、文件哈希和时间；无法确认时明确标记未知。
- 所有权记录区分 CLI 创建、用户已有和用户修改的内容。
- 变更前保存受影响的配置、锁记录和必要文件。失败时恢复可恢复部分，并明确报告无法撤销的外部变更。不得承诺所有外部安装均可原子回滚。
- 卸载前执行路径边界、所有权、哈希和共享使用检查。
- 无法确认所有权时停止删除并报告原因。
- 用户配置、凭证、浏览器登录态和业务项目新增或修改的文件默认保留。项目内未修改的受管理模板文件按所有权记录处理。

## 统一命令行为

- `list` 只读，不改变文件或网络状态以外的缓存。
- 环境和组件的 `check` 不自动安装、升级或删除。`project check` 按既有语义执行测试，可能生成报告和缓存。
- `install/init` 可重复执行，成功后状态应稳定。
- `upgrade` 只输出计划和人工操作建议，不自动安装、替换或更新版本。人工操作后可使用快照回滚。
- `repair` 只补齐缺失或损坏内容。
- `uninstall/remove` 只处理 CLI 拥有的内容。
- 涉及环境的动作支持 `--root`。按对象明确作用域。CLI 提供稳定的机器可读结果，MCP 返回结构化结果。
- CLI、MCP 和文档中的退出码、错误分类和输出字段保持一致。
- 网络不可用时明确返回 `blocked` 或 `unknown`，不能假设“没有更新”。

## 已明确的管理规则

- `env` 管理环境与运行工具。`project` 管理生成项目。`mcp` 管理 MCP。模板和 Skill 使用独立管理入口。
- 当前命令 `skills check-updates` 必须继续可用。新增命令优先沿用 `skills`。若引入别名或更名，须提供兼容期和迁移说明。
- 保留现有 `init`、`uninstall`、`mcp add/remove` 命令。新增能力不能静默改变它们的作用域或删除范围。
- `remove` 和 `uninstall` 按对象区分：移除注册或受管理资产，卸载受管理环境或项目。删除缓存或生成文件须明确目标和路径。不要提供无边界的通用删除命令。环境整体删除范围仍需单独决定。
- 初始化可重复执行。环境检查和更新检查不自动变更组件。项目检查按现有语义运行测试。所有版本升级由维护者人工执行。
- 外部 Skill 使用固定提交。缺失的 MCP 和工具按配置版本安装。复用已有安装时记录实际版本，不将清单版本冒充已安装版本。
- 外部共享软件默认保留。是否继续允许通过 `--include-external` 删除非 QA 安装的软件，见下方待确认事项。
- CLI 不提供交互提示。明确的非交互参数不绕过路径、所有权和共享使用检查。
- 模板清单检查属于模板管理。已有项目的差异与升级建议归入项目管理。CLI 只提供差异与冲突结果，人工应用变更。已修改文件和业务数据默认保留。
- MCP 暴露复用同一业务逻辑的适当能力。环境自卸载和任意命令执行不作为 MCP 工具暴露。
- 文档记录当前行为和规划状态。版本记录只记录实际变化。模板变化同步对应 CHANGELOG。

## 验收条件

- 能区分当前已安装版本、配置基线和上游候选版本。
- 安装和重复执行不会覆盖用户文件或重复注册。
- 升级区分配置基线、安装记录、实际检测版本和候选版本。无法检测时报告未知。能识别旧版、目标版与本地修改。失败后可恢复受管状态，不能恢复的副作用有明确报告。
- 删除和卸载覆盖路径越界、软链接、同名用户配置、多环境共享、已修改文件与未知所有权。
- Python、TypeScript、标准模式和 full 模式覆盖适用的环境与项目场景。
- Windows、macOS、Linux 使用固定 runner。CI 归档失败证据并清理本次测试目录。
- `--help`、使用文档、维护指南、版本记录和实际命令保持一致。

## 仍需确认的删除范围

1. 环境卸载默认保留目录及用户数据。后续需设计可验证的细粒度受管文件清理，以及是否提供显式的整个目录删除操作。
2. 非 QA 软件默认保留。当前 `--include-external` 拒绝执行。后续需要可靠的跨环境引用机制。

## 仍需在实现设计中明确

- QA CLI 发布来源已配置为 GitHub Release。升级仍由用户人工执行，不提供自升级。
- 旧环境和旧锁文件的可迁移版本范围需要根据实际历史样本确认。
- 外部安装器和系统包的回滚能力依赖上游。每个来源必须分别验证，不承诺通用自动回滚。
