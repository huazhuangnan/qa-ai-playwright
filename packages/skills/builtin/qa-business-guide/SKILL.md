# 业务理解与执行引导

先读取 [qa-core](../qa-core/SKILL.md) 公共规则。
先检查项目已有代码、接口契约、文档、测试和配置，再向用户解释。

## 规则

- 接收 PRD、用户故事、验收标准和现有系统资料。记录来源与版本，区分已确认规则、观察、推断和缺口。
- 按任务整理角色、目标、流程、状态、权限及异常，建立需求到用例的追踪。推断须经业务负责人确认。
- 为业务规则、状态、风险和场景分配稳定的 BR-ID、RISK-ID、SCN-ID，记录状态转换、角色×操作×资源矩阵和每个状态的可观察信号。
- 需要保存业务理解时使用 `docs/qa/generated/business-understanding.md`。没有现成 PRD 时可请负责人填写 `docs/qa/inputs/requirements.md`。

- 先判断用户需要“快速理解”还是“实际执行”。
- 说明业务目标和本次范围。
- 列出参与角色、权限边界和责任方。
- 说明入口、前置条件、输入、主流程和可观察输出。
- 说明关键状态、状态变化和不可逆操作。
- 说明异常路径、常见失败和禁止操作。
- 说明如何验证成功、如何清理数据、何时必须停止。
- 区分已确认事实、项目现状、合理推断和待确认项。
- 缺少关键规则时集中列缺口，先完成不依赖缺口的解释。
- 不猜权限、状态流转、业务金额、法律财务影响或生产授权。
- 不把当前页面行为当成业务预期。
- 默认先给最短可执行说明，再按需展开。
- 不索取或写入密码、Token、Cookie、私钥和真实客户数据。
- 涉及生产写入、删除、退款、付款、消息发送等操作时，先说明影响并取得明确授权。
- 业务规则冲突时暂停相关操作，列出冲突来源和需要确认的人。
- 理解业务后再路由到测试设计、API、UI、失败分析或语言适配 Skill。

## 说明

快速理解时按以下顺序输出：

1. 业务一句话说明。
2. 角色和目标。
3. 前置条件、入口和主流程。
4. 边界、高风险操作和待确认项。
5. 建议的下一步操作。

用户需要深入时再补充状态图、异常路径、输入输出和清理方式。

实际执行时补充：

- 当前所处环境和使用的身份。
- 每一步的可观察结果。
- 成功、失败和清理的判定方式。
- 遇到哪些情况立即停止。

资料来源优先级：

1. 用户明确确认的业务规则。
2. 项目需求、接口契约和正式文档。
3. 当前代码和测试所表达的约束。
4. 页面观察和合理推断。

低优先级资料与高优先级资料冲突时，以高优先级为准并记录差异。

用户不需要理解内部实现。
使用业务术语和短句解释。
只提供完成当前任务所需的步骤。
复杂背景按需展开。

## 示例

用户说：“我不懂退款业务，应该怎么测？”

先回答：

```text
业务目标：将已支付订单按规则退回指定金额。
角色：普通用户发起，客服审核，财务处理。
入口：订单详情中的退款入口。
主流程：选择订单 -> 提交原因和金额 -> 审核 -> 原路退款 -> 更新订单与账单状态。
关键边界：可退金额、重复退款、超时订单、部分退款、支付渠道限制。
高风险操作：真实退款、批量退款、修改财务记录。
待确认：谁可审核、可退期限、失败补偿、状态回滚和通知规则。
下一步：先确认退款规则和测试环境，再设计金额、权限、幂等和状态转换用例。
```

若用户要求真实退款，先确认环境、金额上限、回滚方式和授权人。
无法确认时只提供操作说明或测试计划，不执行资金操作。
