# 生成代码质量

生成测试代码时保证一致、可观察、可靠、可控。语言语法按项目现有风格执行。浏览器探索得到的临时步骤必须整理为项目内可重复运行的测试资产。

## 生成契约

生成前先输出简短执行预览，至少包含：

- 文件清单、每个文件的单一职责和依赖方向；
- 用例 ID、测试层级、角色、运行标签和主要断言；
- 数据范围、认证方式、清理方式和证据目录；
- 环境变量、运行命令、浏览器项目和待确认项。

生成后必须逐项核对并报告：结构、注释、断言、清理、证据和实际验证结果。没有执行就标记为未执行，不用静态检查代替运行结果。

## 交付要求

- 测试代码写入项目现有测试目录，并沿用项目脚本、fixture、配置和命名方式。
- 同步生成或更新人工可读的用例文档，至少包含目标、前置条件、步骤、预期、数据、清理和证据。
- 在代码文件或相邻文档中说明运行命令、所需环境变量、浏览器项目和已知限制。
- 生成后保留可 review 的最小 diff；删除探索产生的临时脚本、硬编码账号、真实凭证和不可复用快照。
- 代码必须能脱离当前浏览器会话重新运行；依赖登录态时使用项目约定的 storageState 或认证 fixture。
- 生成的回归代码优先使用项目测试框架和结构化浏览器 API，不把 computer-use 操作序列固化为测试实现；确需保留人工界面操作时，单独标明原因和适用范围。
- 代码生成结果必须标明测试层级：探索脚本不得冒充 smoke 或 regression；只有具备稳定数据、断言和清理的用例才能进入回归目录。
- 录制代码进入项目前必须经过定位器整理、断言补全、敏感信息清理和重复执行检查。
- 每个测试说明 `CASE-ID`、运行标签、浏览器项目和证据目录；失败产物不能依赖当前聊天会话才能访问。

## 结构

- 一个测试表达一个可判定的业务行为。
- 用例名称说明角色、动作和可观察结果。
- 复杂流程按业务结果拆成小步骤。
- 辅助函数只承担一个连贯职责，不隐藏关键断言。
- 复用项目已有 fixture、客户端、页面对象、数据工厂和清理机制。
- 不复制多份认证、HTTP、定位器和清理代码。
- 按职责拆分文件：API、E2E、fixture、页面对象、客户端、数据工厂和 support 不混放。
- 不同业务域、角色或独立生命周期默认分文件；只有共享准备和同一业务行为才放在一起。
- 一个文件出现多个互不相关的业务行为、重复的角色准备或难以定位的失败时，先拆分再继续添加用例。
- 单个测试文件超过两个独立业务行为或约 250 行时，必须评估拆分；只有共享同一业务上下文且拆分会降低可读性时才保留。
- 新文件沿用现有命名和目录；没有明确理由不新建额外层级。

## 注释

- 公共辅助、fixture、页面对象和复杂分支写维护性注释。
- TypeScript 使用 TSDoc，Python 使用 docstring。
- 注释说明业务目标、输入、输出、副作用和非显然约束。
- 复杂测试标明准备、操作、断言和清理流程。
- 简单测试不写逐行复述代码的注释。
- 注释解释为什么，不把代码翻译成自然语言。
- 测试文件顶部或相邻文档说明业务范围、运行方式和限制。
- 每个复杂用例至少能看出 Arrange、Act、Assert、Cleanup；可用 `test.step`、短注释或清晰辅助函数表达。
- 公共辅助缺少用途、输入、输出或副作用说明时，不算完成。

## 一致性

- 同一项目统一测试名、标签、追踪 ID、数据命名、认证入口、等待方式和清理顺序。
- 复用已有 fixture、页面对象、API 客户端和报告字段，不为单个用例创造同义实现。
- 同一业务行为只保留一个权威断言位置；跨层测试按 UI、协议、数据和集成职责区分。
- 代码、用例文档和执行报告使用相同的 CASE-ID、步骤名和状态词。

## 可观察性

- 关键步骤使用业务化步骤名，失败时能定位到角色、动作和结果。
- 断言至少覆盖一个可观察信号：页面状态、响应字段、持久化数据、日志或关联 ID。
- 写入数据带唯一标识，并把请求、实体和证据关联起来。
- 失败保留项目约定的 trace、截图、视频、响应或日志；输出前检查敏感信息。
- 不用元素存在、点击成功、HTTP 200 或固定等待代替业务结果。

## 可靠性

- 测试不依赖当前浏览器会话、上一次运行数据或执行顺序。
- 使用独立 context、唯一数据和确定性等待；不使用固定 sleep。
- 数据和进程的清理或保留遵守[公共执行边界](common-workflow.md)。
- 重试只用于确认稳定性，重试后通过仍标记 flaky，不得用重试掩盖失败。
- 运行前确认服务健康、账号权限、环境和数据边界；缺口写入待确认项。

## 可控性

- 默认拒绝生产写入、真实凭证和未授权外部副作用。
- 所有环境、浏览器、标签、账号和数据范围通过配置或 fixture 集中控制。
- 用例支持按文件、标签和 CASE-ID 单独运行，不要求依赖无关用例。
- 失败时停止在明确边界，保留原始错误和清理结果，不静默降级。
- 生成结果说明未执行项、跳过项、限制和下一步，不把建议写成已验证事实。

## 可读流程

复杂 TypeScript 流程使用业务化 `test.step`：

```ts
await test.step('提交合法表单后看到保存结果', async () => {
  await page.getByLabel('名称').fill(name);
  await page.getByRole('button', { name: '保存' }).click();
  await expect(page.getByRole('status')).toHaveText('保存成功');
});
```

复杂 Python 流程使用简短分段注释：

```python
def test_save_profile(page):
    """保存合法资料后，用户能看到保存成功状态。"""
    # Arrange: 使用隔离用户和唯一资料。
    # Act: 修改资料并提交。
    # Assert: 验证用户可见结果和持久化状态。
```

## 断言

- 断言用户可见结果、契约字段、数据变化或明确业务状态。
- 同一业务行为允许多个互补断言。
- 不用元素存在、按钮点击或 HTTP 200 代替完整业务结果。
- 等待明确页面、响应或业务状态，不使用固定 sleep。
- 失败证据与用例、步骤和运行 ID 关联。

## 类型与可维护性

- 遵守项目严格类型和 lint 配置。
- 不使用 `any` 或动态类型绕过接口。
- 外部响应按 schema 或窄化读取。
- 常量、测试数据和环境配置集中管理。
- 删除本次生成产生的无用导入、变量和辅助函数。
- 优先小函数和清晰数据流，避免为单个断言创建过度抽象。

## 清理

- 使用 fixture teardown、`finally` 或语言等价机制。
- 原测试错误和清理错误分别保留。
- 生成后检查 diff、类型、静态规范和目标用例。

## 审查清单

| 检查项 | 通过条件 |
| --- | --- |
| 业务意图 | 不改业务资料也能看懂测什么 |
| 可读性 | 流程按准备、操作、断言和清理可辨 |
| 复用性 | 使用现有 fixture 和辅助层 |
| 稳定性 | 无固定 sleep、深层选择器和重试掩盖 |
| 可维护性 | 类型明确、职责小、无重复代码 |
| 可诊断性 | 失败时能定位步骤、输入和证据 |
| 人工 review | 文件位置、测试名、步骤、断言、运行方式和限制清楚可查 |
| 可重复执行 | 不依赖浏览器当前状态、上次运行数据或聊天上下文 |
| 数据安全 | 不含真实凭证、Cookie、token 或未脱敏业务数据 |
| 一致性 | 命名、标签、ID、fixture、断言和清理沿用项目约定 |
| 可观察性 | 关键步骤、业务结果、关联 ID 和失败证据可定位 |
| 可靠性 | 可独立、重复、并行运行；清理和错误边界明确 |
| 可控性 | 环境、写入、账号、浏览器和运行范围可配置、可停止 |
