# 生成代码质量

生成测试代码时优先保证可读、可维护、可定位和可清理。语言语法按项目现有风格执行。

## 结构

- 一个测试表达一个可判定的业务行为。
- 用例名称说明角色、动作和可观察结果。
- 复杂流程按业务结果拆成小步骤。
- 辅助函数只承担一个连贯职责，不隐藏关键断言。
- 复用项目已有 fixture、客户端、页面对象、数据工厂和清理机制。
- 不复制多份认证、HTTP、定位器和清理代码。

## 注释

- 公共辅助、fixture、页面对象和复杂分支写维护性注释。
- TypeScript 使用 TSDoc，Python 使用 docstring。
- 注释说明业务目标、输入、输出、副作用和非显然约束。
- 复杂测试标明准备、操作、断言和清理流程。
- 简单测试不写逐行复述代码的注释。
- 注释解释为什么，不把代码翻译成自然语言。

## 可读流程

复杂 TypeScript 流程使用业务化 `test.step`：

```ts
await test.step('提交合法表单后看到保存结果', async () => {
  await page.getByLabel('名称').fill(name);
  await page.getByRole('button', { name: '保存' }).click();
  await expect(page.getByRole('status')).toHaveText('保存成功');
});
```

复杂 Python 流程使用简短分段注释：

```python
def test_save_profile(page):
    """保存合法资料后，用户能看到保存成功状态。"""
    # Arrange: 使用隔离用户和唯一资料。
    # Act: 修改资料并提交。
    # Assert: 验证用户可见结果和持久化状态。
```

## 断言

- 断言用户可见结果、契约字段、数据变化或明确业务状态。
- 同一业务行为允许多个互补断言。
- 不用元素存在、按钮点击或 HTTP 200 代替完整业务结果。
- 等待明确页面、响应或业务状态，不使用固定 sleep。
- 失败证据与用例、步骤和运行 ID 关联。

## 类型与可维护性

- 遵守项目严格类型和 lint 配置。
- 不使用 `any` 或动态类型绕过接口。
- 外部响应按 schema 或窄化读取。
- 常量、测试数据和环境配置集中管理。
- 删除本次生成产生的无用导入、变量和辅助函数。
- 优先小函数和清晰数据流，避免为单个断言创建过度抽象。

## 清理

- 数据创建后立即登记清理。
- 使用 fixture teardown、`finally` 或语言等价机制。
- 原测试错误和清理错误分别保留。
- 生成后检查 diff、类型、静态规范和目标用例。

## 审查清单

| 检查项 | 通过条件 |
| --- | --- |
| 业务意图 | 不改业务资料也能看懂测什么 |
| 可读性 | 流程按准备、操作、断言和清理可辨 |
| 复用性 | 使用现有 fixture 和辅助层 |
| 稳定性 | 无固定 sleep、深层选择器和重试掩盖 |
| 可维护性 | 类型明确、职责小、无重复代码 |
| 可诊断性 | 失败时能定位步骤、输入和证据 |
