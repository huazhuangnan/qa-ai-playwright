# 测试设计

先应用 `qa-core` 已加载的公共执行边界，不重复读取。

## 规则

- 开工前按[输入清单](input-checklist.md)检查资料，缺失项合并列出。
- 检查需求或验收标准、角色与权限、数据生命周期、可观察预期和范围。缺失时保留候选用例并标记待确认，不阻塞有依据的设计。
- 每个功能先应用[通用测试基线](test-design/universal-baseline.md)。
- 基线不足时再读取[功能风险建议目录](test-design/feature-patterns.md)中匹配的章节。推荐不是已确认需求，也不能直接作为通过预期。
- 对每个候选判断业务相关性、风险、资料依据和执行条件。说明保留或不采用的理由，不机械套用目录。
- 新模式加入参考目录，避免在路由 Skill 中持续堆积功能专用规则。
- 选择最小基线和一至三个高风险模式，不把整个候选目录转成正式用例。
- 默认输出 5 至 10 个高价值场景。需要更多时按 P0/P1/P2 分组，并说明扩大范围的原因。
- 产出两份文档：测试计划 `docs/qa/generated/test-plan.md`、测试用例 `docs/qa/generated/test-cases.md`。
- 逐项填写模板字段。不省略字段、不写“同上”、不把多条预期塞进一个单元格。
- 每条用例只验证一个行为，保留需求标识、风险标识、优先级、测试层级、前置状态、数据、步骤、可观察预期和清理方法。
- 用例必须可独立执行和判定。步骤使用单一动作，预期写明对象、状态、时间或数量等可观察信号，不使用“正常”“符合预期”等空泛表述。
- 每条用例定义稳定的 `CASE-ID`、目标、标签、自动化状态、所有者、评审状态和最近复核日期。
- 对关键业务旅程补充有序流程：角色、前置条件、操作、每步可观察结果和清理。关联自动化文件及用例名称。
- 自动化测试应说明业务目标及非显然步骤。复杂流程在报告中使用可辨识的步骤，简单断言不强制包装。
- 预期来自需求或契约。缺规则标待确认，不补造成功码、权限或通过结果。
- 不以用例数量代替覆盖，说明测什么、暂不测什么及原因。
- 用例标注 smoke、regression、integration 等执行标签，并说明 API 门禁是否必选。
- 为关键用例定义证据要求：响应状态和关键字段、页面状态或文本、数据变化、日志、截图、Trace、视频或请求关联 ID。证据必须能支持通过或失败的判断。
- 设计持久迭代字段：来源版本、变更触发条件、最近一次结果、flaky 状态、失败归因、复测关联和下次复核条件。需求或契约变化时先更新追踪关系，再更新用例。
- 计划完成不代表执行通过。未执行就写“未执行”，不写“通过”。

## 说明

- 优先级按影响和发生可能性决定。
- 层级选择：纯逻辑交单元测试，服务行为用 API/集成，关键旅程补 E2E，不在各层重复同一断言。
- 手工执行、需求评审和用例设计不需要创建运行器项目。
- 设计方法：等价类与边界值、决策表、状态转换、角色×操作×资源矩阵。
- 文档质量看两点：能否独立执行，能否独立判定通过或失败。

## 文档产出

测试计划 `test-plan.md` 必须包含：范围、不覆盖项、角色与前置条件、配置变量、API 契约、数据与清理、场景清单、准入退出标准。

测试用例 `test-cases.md` 必须包含：覆盖摘要、关联需求与风险、用例目标、优先级、层级、标签、前置条件、测试数据、单动作步骤与逐步预期、后置状态、清理、证据要求、自动化映射、所有者、评审状态、最近执行结果、flaky 状态、变更触发条件和待确认问题。

## 示例

需求：仅管理员可删除用户，普通用户请求删除返回 403 且不产生删除记录。

```text
CASE-001 管理员删除用户
  关联需求: REQ-001 用户管理
  优先级: P0
  前置条件: admin 已登录，存在隔离用户 u1
  步骤: 1. admin 请求 DELETE /users/{u1}  2. 查询 u1 状态
  预期: 响应 200；u1 已删除且存在删除记录
  清理: u1 为隔离用户，删除后无需恢复

CASE-002 普通用户删除他人用户
  关联需求: REQ-001 用户管理
  优先级: P0
  前置条件: user 已登录，u1 归属他人
  步骤: user 请求 DELETE /users/{u1}
  预期: 响应 403；u1 仍存在且无删除记录
  清理: u1 为隔离用户
```
